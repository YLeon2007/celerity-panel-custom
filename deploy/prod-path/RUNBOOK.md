# Раздел для runbook: S3 / PROD path (черновик, не разрешение на rollout)

Область: выделенный PROD backend на существующем Compose project и выбранные физические роли P/B. Не использовать для TEST, hub-compose, не совпадающего project или неучтённых cohost/писателей. Артефакты здесь не выполняют cutover. Первичное принятие политики, полный старый process tree, writer inventory, исключение альтернативных путей dispatch и независимая эксплуатационная проверка остаются обязательны. Флаги, успешный PID, пустой `ps`, закрытый HTTP и истёкшая аренда этого не доказывают.

### A5: проверить порядок шагов локально (`--dry-run`)

`python3 -I -B deploy/prod-path/activation-scenario.py --dry-run --config <файл.json>` читает только небольшой локальный JSON выбора, печатает порядок действий и `executed:false`. Для сохранённой операции pp16 используйте `{"target":"pp16","mode":"resume","linkId":"6afafb6d991fd12f22e9f457","operationId":"abb507e7fe8a3dae930a20b5"}`. В этом плане **нет** нового apply, переустановки guard, подмены бэкапа или повторного enrollment. План первого отдельного reverse-включения выбирается полями `target=prod`, `mode=first-reverse`, `linkId` (ровно 24 строчных hex-символа). В обоих случаях клиент стоит после подтверждения завершения и снятия удержаний. Адреса, ключи, команды и дополнительные поля в этот файл не входят.

Это планировщик, не разрешение на запуск и не проверка пригодности выбранной связи. Без `--dry-run` он завершается с `LIVE_DISABLED` до чтения конфига. Адаптеры выполнения, сверка фактических квитанций и замеры живых шагов ещё не приняты; на площадках этот сценарий не выполняли.

### 1. Изоляция до подключения нового backend

* Под закрытым admission и в выделенном окне управления инвентаризировать реальных владельцев Docker socket/remote API, Compose/systemd/cron/timer/socket/alias, legacy backend, node agents, SSH/SFTP/installer и другие config writers. Запретить альтернативное создание backend и запись в выбранные профили на всём протяжении, не затрагивая соседние dataplane и management SSH. Не маскировать `xray.service` или `xray-bridge.service` только из-за роли. Неполный inventory — STOP.
* Для старого `hysteria-updater` зафиксировать точный ID/project/service/producer, исключить все пути повторного создания, снять restart policy, остановить с проверкой original PID/дерева/cgroup и исключить уже принятые Docker/BuildKit задания. Затем убрать именно старый контейнер. Существующий stopped updater недостаточен; нет разрешения автоматически запустить его при rollback. У legacy backend снять policy **до** reboot и штатно остановить/проверить прежнее дерево. Не превращать удаление контейнера в `compose down`, чистку volumes или остановку всего Docker. Старый `UPDATE_MODE=source` с Docker socket способен проигнорировать override.
* До разрешения какой-либо загрузки backend установить **постоянные** маски точных принятых writer `.service` (на node `cc-agent.service` включён) с остановкой и проверкой рекурсивно пустой cgroup. Ожидается собственная ссылка `/etc/systemd/system/<unit> -> /dev/null`, не `/run`-маска. Учитывать aliases, старые jobs, trigger units и внешний dispatch отдельно: v2 guard проверяет только принятые service pins. Если на месте маски стоит локальный unit fragment, `systemctl mask` недостаточен: сначала согласовать узко scoped перенос точного fragment и его aliases из unit search path, затем проверить effective mask. Не перезаписывать вслепую. Не отключать выбранный management SSH.
* `systemd/c3-prod-isolation.service` не меняет host state: проверяет возможности и native mask/cgroup predicates. На каждом физическом host/node поставить и квалифицировать `c3-prod-isolation` → `c3-prod-guard`; backend unit — только на панели. Guard native v2, без `Restart=` на успех/падение, без rearm/очистки socket/lock/journal. `ExecStartPost` подтверждает LISTEN того же guard PID и удержание flock без подключения: пробный `connect` от неправильного peer способен отравить guard. LISTEN не доказывает непротухшую authority; её проверяет настоящий observer.
* `c3-prod-backend` — единственный boot/launch path, после Docker, isolation и guard (`BindsTo` + `After`). Отключить старый autostart/ручные и scheduled `up`/self-update пути до его включения; не включать все units `--now` на этапе установки. Guard/бекенд не делают автоматических перезапусков. Обычная остановка ждёт native drain: допустимое окно Compose 35 мин и systemd 36 мин, не считать forced stop чистым. Не останавливать guard как способ перезапустить один backend.

### 2. Интерпретаторы и установленные источники

Поставить как принятые root-controlled **исходники** (`root:root`, leaf 0600 или 0700; предки не writable, без symlink):

| Источник | Путь установки |
|---|---|
| `scripts/prod-maintenance/{authority_helper,exclusion_guard}.py` | `/usr/local/libexec/c3-prod-maintenance/` |
| `scripts/production-topology-physical.py` | `/usr/local/libexec/c3-production-physical.py` |
| `scripts/test-node-isolation/original_effects.py` | `/usr/local/libexec/c3-production-original-effects.py` |

`/opt/hysteria-panel` — принятый корень этого пакета, unit-файлы используют этот путь. `topology-production-node.json`, `prod-admission-exclusion.json` и панельный `topology-production.json` — **независимо принятые**, не образцы; не генерировать их из старого DB/access log. Root-private каталоги `/etc/celerity`, `/var/lib/celerity/production-physical`, `/var/lib/celerity/prod-path/guards` и root:root 0600 regular `backend.launch.lock` под `/var/lib/celerity/prod-path` готовятся явно; не создавать original/binding/restore records. Native lock/journal/socket guard должны быть новыми именами в private каталоге при первом запуске.

На **каждом** участнике `/usr/bin/python3.13 -I` — точный guard argv/executable pin. `/usr/bin/python3 -I -B` — точный argv observer, distro Python ≥3.10; `/usr/bin/python3` используется и shell/SFTP runner. Не менять системный symlink и не копировать Python/Xray binaries с панели; используйте штатный пакет из принятого репозитория/образа для каждой целевой ОС, устанавливая 3.13 параллельно. Если путь/пакет отсутствует, нужен согласованный поддерживаемый OS image/upgrade с тестом установленного ABI, не override pin. На Ubuntu 22.04 наличие 3.10 не доказывает наличие 3.13; наличие обоих не доказывает поддержку kernel `SO_PEERPIDFD`. Штатная проверка — `/usr/bin/python3.13 -I -B /opt/hysteria-panel/deploy/prod-path/preflight.py isolation` при установленных source/policy/masks: строгий argv не модифицируется; проверяются компиляция под фактическим python3, pidfds, `SO_PEERPIDFD` на живой локальной паре и cgroup v2. Нет fallback на PID.

### 3. Compose и контейнерный SSH

Использовать проверенный Docker Compose ≥2.24.4: `docker-compose.yml` **затем** `deploy/prod-path/compose.override.yml`, с тем же `--project-name` и `--project-directory`. В root-private `/etc/celerity/c3-prod-backend.env` — только явно принятые `C3_PROD_COMPOSE_PROJECT` и `C3_PROD_BACKEND_IMAGE` (`name@sha256:…`, образ содержит этот пакет и уже установлен локально). Поднять/проверить отдельно точные retained Mongo/Redis; unit не пересоздаёт зависимости. Caddy и его тома не меняет unit. Не запускать `compose up -d` без указания цели/override. Верификатор проверяет rendered backend модель и отсутствие legacy updater, не печатает отрендеренный config. Для прибора `config --services`/`--quiet` достаточно ограниченного вывода; не выводить env/inspect всей конфигурации. `TOPOLOGY_PRODUCTION_EXECUTION_ENABLED` включает только штатную PROD topology assembly; отдельный L2TP PROD executor оставлен отключённым.

Каталог `/etc/celerity` и находящиеся в нём identity keys входят в контейнер одним RO bind без `create_host_path`; не класть туда лишние секреты и writable submounts. Политика и ключи — root:root (`0600`), родитель `0700`; backend — UID:GID `0:0` **с фактической видимостью тех же UID/прав**. User namespace/LSM/ACL несовместимость — STOP; не `chmod 644` и не `privileged`. Нет mount Docker socket/checkout. `config.host.endpoint.ip` — реальный маршрутизируемый из Compose namespace адрес выбранного хоста, который sshd действительно возвращает как server addr в `SSH_CONNECTION`; не `localhost`, не gateway-алиас вслепую, не `host.docker.internal`. Числовые addr+port, root key auth, SHA-256 **raw SSH host key**, не `ssh-keyscan` как источник принятия. Проверить allowed ingress отдельно, без расширения сетевых правил «чтобы заработало»; добавить собственный ключ к подходящему серверу только после отдельного допуска. Используется native SSH verifier/command/observer перед `index.js`, без DB/dispatch, проверяются host и обе роли. Эта проверка не доказывает bootstrap SFTP, учётного разрыва old writers, readiness данных или client traffic; SFTP квалифицируется отдельно в разрешённой rehearsal. Не запускать ручной observer поверх активного backend: guard v2 обслуживает последовательных holders и ждёт выхода предыдущего процесса.

### 4. Reboot / boot ID: только standalone panel host

* Keep closed. После reboot старый boot pin обязан отказать; guard v2 не означает межboot succession. Reconnect backend при том же boot — к **тому же** живому guard (после естественного выхода прошлого helper), без нового boot/holder. При внезапном guard death/poison на том же boot нет штатного respawn; не удалять lock/journal/socket и не «чинить» runtime pin.
* Штатный `rebind-boot.py` допускает **только** `mode:runtime` отдельного panel host (`kind:host`, один guard). На ко-хосте или при новом boot P/B — STOP: `originals.json` привязан к старым physical/guard pins, journal/enrollment/operation bindings — к boot ID. Этот пакет не меняет ни один из них. Нужен отдельно принятый supported recovery / maintenance decision; не использовать TEST pristine resume и не подставлять текущий boot или обнулять журнал.
* Заранее сохранить доступ к точным прежним принятым политикам, включая отдельно root-private bytes прежнего guard policy в `/etc/celerity`, и независимые SHA-256 прежних panel/host/guard. Удержать маски и исключение, остановить/закрыть запуск backend и прежний guard, сверить отсутствие updater и пустые деревья предыдущих писателей. Из доверенной консоли независимо подтвердить reboot, **тот же** machine/key/endpoint и согласованный новый boot ID. Не подставлять полученный из того же probe ID или digest автоматически. Помнить, что checker не самодоказывает эксклюзивное окно.
* Команды ниже — шаблон оператора для будущего окна; переменные вводятся из отдельно принятого решения, не через `$(cat …)`. `previous_guard_policy` — сохранённая принятая **политика**, не runtime journal. Подкоманда `guard` сохраняет mask set/challenge/maintenance, публикует только guard policy с отдельным поколением ресурсов. После неё backend ещё не допускается.

```bash
rebind=(/usr/bin/python3.13 -I -B /opt/hysteria-panel/deploy/prod-path/rebind-boot.py)
accepted=(--project "$project" --accept-boot "$accepted_boot" --old-panel-sha "$old_panel_sha"
          --old-host-sha "$old_host_sha" --old-guard-sha "$old_guard_sha")
"${rebind[@]}" guard "${accepted[@]}"
# Только при успехе и независимо проверенном порядке:
systemctl start c3-prod-guard.service
"${rebind[@]}" inspect "${accepted[@]}" --previous-guard-policy "$previous_guard_policy"
# Сверить live PID/start/argv/executable/source, lock/generation, адрес и прежние узлы;
# независимый reviewer отдельно принимает hash кандидата host policy.
"${rebind[@]}" publish "${accepted[@]}" --previous-guard-policy "$previous_guard_policy" \
  --accept-host-sha "$accepted_host_policy_sha"
```

`publish` перепроверяет boot, маски, live holder/lock и прежние hashes; меняет локальные host/guard references и host boot, не трогает `nodes`, originals, leases или операции. Сначала обновляется локальная host-helper policy, затем panel policy (каждый файл atomic+fsync). При прерывании между файлами native observe откажет из-за mixed pins. Новый запуск/повтор команды при частичной публикации не допускается: удержать изоляцию и передать точное состояние на отдельную сверку, не редактировать JSON и не откатывать boot pin назад. `publish` не стартует backend; его возможный ручной/boot start всё равно проходит полный gate. Наличие нового host guard не означает, что обе выбранные роли стали готовы.

#### Выбранный guest B → P: блокировка S3 для A5

Перед B6 и B7 A5 проверяет поддержку выбранного гостя **до перезагрузки**. Для локальной проверки: тот же `activation-scenario.py --dry-run --config` с `{"target":"pp16","mode":"B6","linkId":"6afafb6d991fd12f22e9f457"}` (для P — `B7`). В обоих случаях CLI вызывает только локальный запрос возможности `guest`, возвращает `executed:false`, пустой список шагов, причину блокировки и exit 1. Отказ — не успешная репетиция B6/B7. Не перезагружать даже первого гостя B; не подменять его общим B2 или отдельным хостом панели.

Offline-интерфейс для **явного запроса** межboot-перехода выбранной роли: `python3 -I -B deploy/prod-path/rebind-boot.py guest --role B` (также `P` или `cohost`). Результат: exit `1`, одна строка stdout `C3_REBIND_REFUSED:SELECTED_GUEST_BOOT_TRANSITION_UNSUPPORTED`. Это неизменяемый в этой версии отказ, не детектор reboot и не live preflight. Не передавать boot ID, policy hash или путь к журналу. В A5 проверять перед эффектами; при отказе на B не переходить к P, не стартовать backend для обхода и не открывать release gate. Не вызывать `guard/inspect/publish` для выбранного гостя или панели-cohost.

Блокировка не сводится к несовпадению SSH/boot pin. `production-topology-physical.py` требует при `attach` исходные physical/guard pins в неизменном `originals.json` и exact `binding.json`; после обновления только policy `observe` без runner journal может пройти, а `attach` — нет. При наличии v2 journal даже `status` для уже закрытой генерации на новом boot возвращает `BOOT_CHANGED_UNCERTAIN`. PROD runtime дополнительно сравнивает boot в принятом enrollment; `verifyPristineEnrollment` разрешён только в TEST и не для истории с bindings/locks/operations. Нужен отдельно принятый native переход, который доказывает ту же машину/ключ/endpoint, непрерывное исключение старых писателей и новые live guard holds, согласует originals, ownership и runner/DB lineage **без замены исторических фактов**. Ни новый guard, ни истёкший lease, ни принятые новые policy hashes этого не доказывают.

Обычный контейнерный `preflight-ssh.cjs` в `runtime` до `index.js` теперь проверяет `observe → attach/read` для обоих принятых originals. В `enroll` остаётся только `observe`: preflight не вызывает `capture`, не пишет DB и не делает runner dispatch. Успех означает возможность attach в текущем boot, а не `closing → succeeded`, release или разрешение переключить writer. Отказ не изменяет удержанные данные. Ночной reconnect pp16, resync через held runner при маскированном агенте и settlement удержанного closing остаются путями **того же boot**, не образцом межboot-перехода.

### 5. Readiness, восстановление и пределы

* Бюджет для окна выбирать по сохранённой ночной шкале: startup ~33 мин, apply→closing 53+ мин, отдельные интервалы ~4–14 мин. Это отметки событий, не измерения длительности SSH/DB/systemd и не новый lease/SLA. Аренда partial P, затем другая retained verified closing и отказы resync — разные границы. Не ждать «ещё немного» ценой replay: зависимости и обычная startup readiness проверяются отдельно, оставлять запас на диагностику/штатное завершение.
* С маскированным classic agent нельзя возвращать resync через HTTP/unmask. Принятый backend использует штатный held runner для topology-owned resync; на closing требуется проверка P и B независимо, их readback + native proof/finalizer, не только ответ одного cohost или successful SSH. При UNKNOWN/неполной паре сохранить операцию, leases/locks/admission и originals; не повторять apply/commit и не считать closing→succeeded без штатной проверки.
* При сравнении rollback/нового старта сохранять volumes, Caddy, выбранные профили и закрытый admission. Остановка нового backend либо возврат старого образа сами по себе не handback и не разрешают запуск отменённого updater/agents. Любое разрешение writer-enable — только через отдельный поддерживаемый verified handback.
