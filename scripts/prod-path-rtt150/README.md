# S1: локальная репетиция первого reverse apply при RTT 150 мс

Это диагностическая fixture, не активация PROD и не восстановление pp16. Она
ничего не добавляет в production startup, worker, state machine или CI matrix.

## Как повторить

Из корня своего worktree, обычным пользователем на Linux, с уже установленными
зависимостями Node и имеющимися `mongod`, `xray`, `geoip.dat`, `geosite.dat`:

```sh
TOOLS=/home/leon/.hermes/cache/scratch/c3-fast-tools
node --test scripts/prod-path-rtt150/probe.test.cjs
env -i PATH="$PATH" node scripts/prod-path-rtt150/run.cjs 0 "$TOOLS"
env -i PATH="$PATH" node scripts/prod-path-rtt150/run.cjs 150 "$TOOLS"
```

Запускать последовательно. Каждый запуск создаёт новый replica set и
`.s1-*` в этом worktree, завершает свои процессы и удаляет каталог; сохраняйте
выходную строку `S1 {…}`. Exit 0 — только локальный e2e строго <300 с **в сумме**
и успешная уборка; exit 1 включает доказанный, но слишком медленный e2e.
Наблюдение apply ограничено 360 с, отдельно от порога 300 с. Timeout, отказ,
HTTP 202, `closing` и `succeeded` без независимого клиентского прогона — не PASS.
Внешний watchdog должен оставлять время на штатный drain (не убивать через
300 с); команда не меняет прикладные lease, timeout, worker tick или часы БД.

## Что и где измеряется

- **RTT:** 75 мс перед выполнением и 75 мс перед возвратом результата каждого
  прикладного panel→guard запроса или panel→node runner RPC, в том числе при
  ошибке. Пять пустых последовательных вызовов через тот же эмулятор дают
  `calibrationMs`; `0` — контроль с тем же кодом без задержки. Это не эмуляция
  TCP/SSH handshake, пакетного RTT, TCP-конгестии, джиттера или потерь. Mongo,
  входящий HTTP и клиентский трафик Xray остаются без искусственной задержки.
- **Startup:** `rootStart` (вызов post-DB PROD root) → `fixtureReady` (HTTP 200 с
  корректным телом от fixture после барьера startup). Включены настоящая
  проверка каталога/индексов, enrollment и запуск штатных consumers. Подъём
  Mongo и создание схемы происходят **до** старта таймера; полный `index.js`,
  Redis, Caddy/TLS, Compose, системные preflight/unit и прикладной `/health`
  не запускались. `marksMs.rootStart` показывает длительность подготовки с
  момента старта fixture, а не время production startup.
- **Apply:** `post` (отправка единственного настоящего `POST /api/cascade/links`
  с `autoDeploy:true`) → `clientProof`. HTTP 202 — `ack`, отдельно. В интервал
  входят штатное ожидание worker tick, durable intent/admission, планирование,
  выход команд runner, `closing`, проверка пользователей, терминальные proof
  и освобождение удержаний; метки состояний — момент первого readback, не
  момент записи. Требуются та же операция `succeeded`, две terminal proof,
  ноль locks/обоих admissions, deployed link и совпадение файловых хешей с
  замороженными кандидатами. После этого отдельный Xray клиент должен получить
  уникальный ответ локального HTTP origin по VLESS → Portal → reverse → Bridge.
  Прямой egress Portal блокируется, чтобы он не давал ложный PASS. Это внешний
  client probe fixture, **не** изменение `clientReadiness` в продуктовой БД.
- **Сумма:** `rootStart` → `clientProof`, включая небольшой промежуток между
  готовностью и POST. Все интервалы основаны на `performance.now()`; метки runner
  относятся к возврату RPC, а не к одному системному вызову.

Реальны HTTP-маршрут, PROD lifecycle/планировщик/worker, Mongo-транзакции,
V2 runner и его журналы, парсинг Xray оригинальных кандидатов, локальные
перезапуски Xray и трафик. Авторизация HTTP, физический guard/состояние
старого писателя, SSH/SFTP и systemd моделируются. Для процесса Xray создаётся
**отдельная** локальная проекция кандидата: listen только на loopback, без
sniffing/DNS, egress Bridge ограничен локальным origin; файл кандидата для
runner и его проверок не заменяется этой проекцией. Исходные профили пустые,
ровно два узла (панель совмещена с Portal), TCP/VLESS без TLS/REALITY, один
синтетический пользователь, без PPP и production-инвентаря. Нет обращения к
стендам, внешней сети, DNS, `.env`, реальным секретам или host `tc`; не копируются
бинарники. Это не эквивалентность сетевым/физическим условиям PROD.

## Измерения

Код продукта `a589588512d53e767743eee9cba1a0db1f66abf6`; Node 22.23.1,
Mongoose 8.24.1, MongoDB 8.0.16, Xray 26.3.27. Последовательная пара на свежих БД,
без подмены часов. В таблице секунды, кроме калибровки:

| RTT модель | Echo (5, мс) | Startup | POST→202 | POST→preparing | POST→closing | POST→durable readback | POST→client proof | Startup→client proof |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 мс | 0,001–0,078 | 0,554 | 0,100 | 30,278 | 34,348 | 37,192 | 37,313 | 37,867 |
| 150 мс | 150,680–151,705 | 95,741 | 0,093 | 32,667 | 178,503 | 290,172 | 290,288 | **386,029** |

В обоих запусках: `succeeded`, proofs 2/2, locks 0, admissions 0/0, точные хеши
обоих staged кандидатов, один подтверждённый запрос к origin, уборка завершена.
На границе замера строка intent ещё `admitted`, встроенный `clientReadiness`
ещё `unverified`; замер заканчивается по операции и отдельному клиенту, не по
публикации job/UI. При 150 мс обе фазы по отдельности уложились, но суммарная
цель <300 с **не достигнута**: превышение 86,029 с, `local-e2e-over-budget`, exit 1
(не timeout). Предыдущий диагностический прогон 150 мс, до добавления общей
проверки порога: 95,779 с / 290,146 с / 385,925 с, также с локальным client proof.

В обоих финальных запусках 630 guard RPC до готовности, затем ещё 1668 guard и
16 runner RPC до завершения. Это счётчики, а не сумма длительностей SSH или
разложение исторического критического пути. Сохранённые pp16: startup 32:50,
POST→closing 53:08, успешный apply не наблюдался; причина неизвестна. Эти отметки
не являются baseline с тем же endpoint и не доказывают ускорение. Три теста
fixture прошли (симметрия задержки/ошибка, строгий порог, loopback-проекция).
