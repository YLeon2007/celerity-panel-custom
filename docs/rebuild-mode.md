# Режим rebuild

`C3_REBUILD_ENABLED=true` — отдельный режим запуска панели. По умолчанию он
выключен (`false` или переменная не задана). Другие значения отклоняются.
Проверка выполняется после загрузки `.env`, до подключения MongoDB и старта
сервисов. Режим читается из окружения процесса, не из HTTP-запроса.

При включении следующие флаги должны быть не заданы либо равны `false`:

- `L2TP_EXECUTION_ENABLED`, `L2TP_MIGRATIONS_ENABLED`, `L2TP_PRODUCTION_EXECUTION_ENABLED`;
- `TOPOLOGY_TEST_EXECUTION_ENABLED`, `TOPOLOGY_PRODUCTION_EXECUTION_ENABLED`;
- `CLASSIC_TOPOLOGY_PRODUCTION_EXECUTION_ENABLED`, `CLASSIC_TOPOLOGY_LIFECYCLE_ENABLED`.

`TOPOLOGY_TEST_STARTUP_MODE` и `C3_SETTINGS` должны быть не заданы. Последний
включает отдельный режим с зафиксированной схемой настроек; rebuild не входит
в этот контракт. Неактивные параметры (например, список разрешённых связей)
сами по себе ничего не включают.

В rebuild не запускаются L2TP/topology bootstrap, миграции, проверка и
автоматическое создание их схем, admission/recovery workers, физическая
authority или возобновление привязок. HTTP отклоняет строгие пути деплоя,
операций, замены, transfer, активации/возобновления, проверку порта scoped deploy
и L2TP; MCP отклоняет `manage_cascade`. Обычные сервисы запуска, опрос агентов,
cron и `/health` не выключаются. Чтение графа и подписок остаётся доступно;
проверки владельцев конфигурации не отменяются. `/health` не подтверждает
готовность rebuild-writers или передачу владения.

## Формат туннеля и первый Apply

Rebuild использует VLESS Reverse Proxy: `reverse.tag` в записи туннельного клиента на портале и `settings.reverse` у исходящего подключения бриджа. Первый подтверждённый Apply заменяет legacy reverse на обоих концах. Предпросмотр указывает переход отдельно от изменений клиентских входов. Для VLESS без TLS/REALITY на каждую связь используется отдельная пара ключей VLESS Encryption. Панель сохраняет ключ связи в MongoDB только в зашифрованном виде после подтверждения; Preview и повторный Apply ключи не меняют. Не меняйте `ENCRYPTION_KEY` в процессе миграции.

На всех затронутых нодах панель проверяет фактическую версию `/usr/local/bin/xray`: неизвестная версия или версия ниже **25.9.11** блокирует операцию до записи профилей. До первого рестарта все кандидаты проходят локальный `xray run -test` на нодах. Для локального HTTP-теста нужны реальные бинарники `C3_XRAY` (26.3.27) и `C3_XRAY_26_11_9` (26.11.9) с geo-ресурсами рядом с бинарниками. Это проверка формата, не проверка живого PPP.

## Apply, AutoDeploy и DELETE

Выберите связь на карте. Предпросмотр читает MAIN и BRIDGE каждой ноды всей связной схемы и показывает изменившиеся разделы без UUID, ключей и полных конфигов. Если изменится клиентский вход, панель не пишет **ни на одну** ноду. Изменения туннеля допустимы. Для каждого клиентского REALITY-входа портала проверяется также публикация: публичный ключ из БД должен соответствовать приватному ключу сервера. Самих ключей в отчёте нет. Отмена в окне предпросмотра не отправляет конфиги; уже сохранённый черновик связи остаётся в БД.

HTTP-клиент получает отчёт через `POST /api/cascade/rebuild/preview` с `linkId` (для удаления также `remove: true`). Для Apply передайте `linkId` и `expectedPreview: previewId` в `POST /api/cascade/topology/deploy`. Для удаления передайте `expectedPreview` в теле `DELETE /api/cascade/links/:id`. Отсутствующий предпросмотр — HTTP 428, устаревший — `REBUILD_PREVIEW_CHANGED`. Токен удаления не взаимозаменяем с токеном Apply. При создании/редактировании с `autoDeploy: true` возвращаются `linkId`, `status: awaiting_preview` и `preview`; интерфейс показывает этот отчёт и продолжает Apply после подтверждения, без повторного создания связи. Сохранение черновика не означает применения.

Перед заменой файлов выполняется проверка всех кандидатов парсером Xray. Панель устанавливает пару профилей на каждой ноде, перезапускает нужные службы, затем перечитывает оба профиля на всех нодах. Это **не** одновременная атомарная запись на нескольких хостах. После обрыва возможна частично применённая схема: запросите свежий предпросмотр и повторите Apply той же связи. Для незавершённого DELETE в БД остаются её концы, чтобы повторный Apply охватил обе прежние части. Нет фонового продолжения или автоматического отката.

На панель действует одна запись-блокировка в MongoDB. Если процесс оборвался, оператор проверяет отсутствие выполняющегося Apply и снимает устаревшую блокировку кнопкой на карте. Блокировка не исчезает по TTL. Отправка пользователей агенту и запись конфигов сериализованы на ноду внутри процесса панели; поздняя запись внешним агентом или updater после перечитывания этим не исключается.

Для установленного L2TP сохраняются PPP, TPROXY и прежняя route group. В MAIN релея стабильный локальный SOCKS входит в правила абонентов: запреты, geo, затем приоритетный выход либо `block`. Смена бриджа не требует редактировать `paths.linkIds`. Правила strict-режима и его старая история не снимаются операторской кнопкой rebuild. Существующий strict-стенд с удержаниями не является свободной целью.

## Смена роли L2TP-релея

В rebuild форма `/panel/nodes/:id`, `PUT /api/nodes/:id` и MCP `manage_node`
не переводят релей в другую роль, пока его управляемое состояние L2TP не
`not_installed` без намерения установки. Отсутствие записи состояния — штатный
случай неустановленного L2TP; ошибка чтения не считается отсутствием. Запись
роли берёт ту же Mongo-блокировку Apply и затем тот же локальный lock ноды,
что и Install/Remove: роль и состояние перечитываются до записи под lock.

N в сообщении — точное число записей MongoDB `L2tpUser` с `relayNode` этой ноды,
включая отключённые и ожидающие синхронизации. Это не инвентарь `chap-secrets`
и не подтверждение права на удаление. M определить нельзя: у rebuild нет
источника числа активных PPP/L2TP-сессий по релею. `onlineUsers` относится к
Xray/Hysteria, а `vpn_empty` в `rebuildRelayDirectHost.py` — внутренняя булева
проверка отсутствия PPP/XFRM для операции, не счётчик. `prepare-remove`
возвращает отпечаток состояния, а не число сессий. Поэтому форма пишет
«сессии не подтверждены» и не добавляет кнопку удаления с неподтверждённым
счётчиком. Существующий `POST /panel/rebuild/relays/:id/l2tp/remove` и его
проверки владения установкой/учёткой не изменены.

## Подготовка xl2tpd для нового L2TP-релея на Debian 13

Это отдельная операторская предпосылка **только для rebuild**. На целевом
реле из доверенной копии репозитория, от `root:root`, в окне без параллельных
установок и изменений unit-файлов или служб выполните:

```sh
/usr/bin/python3 -I -B src/services/rebuildRelayStockRuntime.py &&
    /bin/bash src/modules/relay-l2tp/node-artifacts/l2tp/install-runtime.sh
```

Порядок обязателен: штатный `install-runtime.sh` может дополнить
`/etc/ipsec.conf`. При отказе предпосылки не запускайте его. Это не операция
HTTP, не `DIRECT prepare/check` и не изменение запуска Classic.

- Поддерживается установленный Debian trixie `xl2tpd:amd64 1.3.18-1+b1`.
  `/etc/init.d/xl2tpd` и `/etc/default/xl2tpd` должны совпасть с исходными
  файлами пакета по SHA-256, владельцу и режиму. Отклоняются даже изменения
  комментариев, симлинки и отклонения (`dpkg-divert`). Пакет не устанавливается
  и не переустанавливается этой предпосылкой.
- `created`: допускается только неактивная штатная SysV-обёртка в
  `/run/systemd/generator.late` с исходным `SourcePath`. Проверяются точные
  байты вывода генератора Debian systemd 257.13 для штатных уровней запуска
  2–5 или без start-ссылок, владелец, режим и ссылки, включая `l2tpd.service`.
  Существующий `ensure-xl2tpd-unit.py` эксклюзивно создаёт только
  `/etc/systemd/system/xl2tpd.service`; после `daemon-reload` проверяется, что
  загружен именно этот неактивный native unit (`root:root`, `0644`, без
  drop-in). Предпосылка не запускает и не включает службу.
- `native-present`: этот же native unit уже загружен, неактивен и не включён;
  изменений и `daemon-reload` нет. `stock-not-found`: обе формы имени
  отсутствуют на диске и в systemd, а SysV-генератор отсутствует или штатно
  замаскирован через `/dev/null`. Предпосылка ничего не пишет; native unit
  создаёт штатный `install-runtime.sh` по исходному пути `not-found`.
- Маска самого `xl2tpd.service`, другой unit, drop-in, устаревшее состояние
  менеджера, активность или непустая очередь systemd блокируют продолжение.
  Если ошибка возникла **после** создания файла (например, при reload или
  проверке результата), новый файл может остаться; автоматического удаления
  и повтора нет. Проверьте состояние на месте, прежде чем продолжать.

Хеши получены из пакетов amd64, проверенных по `Packages` из подписанного
`InRelease` Debian trixie 13.7: `xl2tpd_1.3.18-1+b1_amd64.deb`
(`dd6fdf32b90f9f7d516f5251e1abdb65851156c80163a41aab60cf94dcff16da`) и
`systemd_257.13-1~deb13u1_amd64.deb`
(`ee81302a1d5b7434762b6e784a572854d4b6cf6235e33e2d104ad4e1cae71ab4`).
