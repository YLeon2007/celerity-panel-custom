# ТЗ: Topology Domains + multi-portal fan-in (Celerity Panel)

Дата: 2026-09-25. Статус: черновик на согласовании. Исполнение — только после явного «давай».

## 1. Цель

Поддержать в новой topology-модели схему, запрошенную для прода:

```
домен 1:  4 портала ─┐
                     ├─→ релей1 (→ …цепочка релеев) → бридж-дефолт
                     │                            ↘ бридж-RU (geo-лист)
домен 2:  4 портала ─┴─→ релей2 → бридж-дефолт ↘ бридж-RU (geo-лист)
```

То есть две независимые возможности:

1. **Topology domains** — несколько независимых графов (доменов) в одной панели,
   каждый со своим жизненным циклом draft → validate → pin → deploy.
2. **Multi-portal fan-in** — внутри одного домена несколько порталов
   (входных нод) сходятся в общую цепочку.

## 2. Текущее ограничение (v1.3.3.12)

- `CascadeTopologyState` захардкожен как документ `singleton` — одна ревизия,
  один pin, один деплой на всю панель.
- Валидатор требует ровно 1 портал на весь граф и одну линейную
  основную цепочку; ветвление — только geo-листья.
- L2TP route groups / `auto-l2tp` path строятся по единственной
  default-цепочке панели.

Прод-граф (8 порталов / 9 бриджей) новым механизмом не деплоится (fail-closed),
legacy-управление при этом полностью сохраняется.

## 3. Дизайн: домены

### 3.1. Домен = связная компонента графа

Явной сущности «домен» (CRUD, имя) НЕ вводим. Домен определяется структурой
связей: каждая связная компонента графа `CascadeLink`, содержащая хотя бы одну
ноду, — отдельный домен. Идентификатор домена — детерминированный ключ от
набора нод компоненты (например, минимальный nodeId в компоненте; при слиянии/
разбиении компонент ключи пересчитываются — это нормально, т.к. меняется и сам
граф).

Плюсы: невозможно рассинхронизировать «домен» и граф; legacy-цепочки
автоматически становятся доменами (своими компонентами) без миграции данных.

### 3.2. Per-domain состояние

- `CascadeTopologyState`: вместо `_id='singleton'` — `_id='domain:<key>'`.
  Документ `singleton` при апгрейде мигрируется: если граф один — в его домен;
  если компонент несколько — singleton остаётся пустым/архивным, деплой
  требует явного per-domain черновика (fail-closed, как сейчас).
- Draft (pin/validate) — per-domain: черновик содержит срез ссылок одной
  компоненты; валидация и pin работают в её границах.
- Деплой — per-domain: транзакция, план, квитанции нод, операции — всё со
  скоупом домена. Деплой домена A не трогает ноды домена B.
- Node-level operation locks уже существуют и дополнительно страхуют от
  пересечений (нода физически не может входить в два домена — компоненты
  не пересекаются по определению).

### 3.3. Staged-ноды

Роли по-прежнему только ручные. Roled-нода без связей — staged asset, не
входит ни в один домен, не мешает валидации (текущее поведение сохраняется).

## 4. Дизайн: multi-portal fan-in

### 4.1. Правила формы домена

Внутри домена разрешено:

- **Порталы (≥1)**: только исходящие связи; входящих нет. Все порталы —
  источники трафика.
- **Релеи**: линейная цепочка; точка слияния (merge point) — первый релей,
  в который входят ≥2 связи от порталов/релеев. Fan-in разрешён только
  «слева» (со стороны входа): несколько входящих связей у релея — да;
  несколько исходящих — только по правилу geo-листьев.
- **Бридж-дефолт (ровно 1)**: конец единственной non-geo ветки. Нужен для
  однозначного default-маршрута (в т.ч. L2TP).
- **Geo-бриджи (≥0)**: листья с `geoRouting`, без исходящих связей.

Запрещено: циклы; портал с входящей связью; бридж-дефолт с исходящими;
несколько non-geo веток; geo-лист с исходящими; «серединное» ветвление
без geoRouting.

### 4.2. Валидатор

`topologyValidator` переписывается с «один граф = одна цепочка» на
проверку формы домена по правилам 4.1. Ошибки — с кодами и указанием
нод/связей (как сейчас). Staged-ноды игнорируются.

### 4.3. Компилятор и конфиги

- Каждый портал получает свой inbound-конфиг, указывающий на следующую ноду
  своей ветки (наследование REALITY destination/SNI из target-ноды
  сохраняется; явные значения связи имеют приоритет — текущее поведение).
- На релее в точке слияния — несколько входящих ingress (по одному на портал),
  далее единый egress к следующему релею/бриджу.
- Geo-routing rules применяются на ноде развилки и на L2TP ingress
  (текущее поведение e8a7e5e сохраняется).
- IPv6 fast-reject (903299f) — без изменений.

### 4.4. L2TP

- Релей привязан к домену (выводится из компоненты); `auto-l2tp` route-group
  path строится внутри его домена от точки релея до бриджа-дефолт.
- Несколько L2TP-релеев в разных доменах сосуществуют; route groups,
  operations, health — со скоупом домена.
- L2TP на портале fan-in домена — вне скоупа этого ТЗ (только релеи),
  при необходимости — отдельной фичей.

## 5. UI

- Карта топологии: группировка по доменам (визуально — отдельные «острова»,
  как сейчас по компонентам).
- Вкладка топологии: селектор домена → свой черновик, валидация, pin,
  кнопка деплоя, список операций и health по домену.
- Legacy-домены (не проходящие валидацию новой формы) отображаются с меткой
  «legacy — управление классическим способом», кнопка нового деплоя
  недоступна (fail-closed, как сейчас).

## 6. Миграция и обратная совместимость

- Данные связей/нод не мигрируются (компоненты выводятся из графа).
- `singleton`-документ состояния: миграция по 3.2; откат кода на ≤v1.3.3.12
  безопасен — старая версия снова видит singleton (per-domain документы
  игнорирует). Mongo RS — уже на месте.
- Классические маршруты (`cascadeLinks`, `/cascade/chain/deploy`) не
  затрагиваются: legacy-цепочки продолжают обслуживаться старым способом
  независимо от новых доменов.

## 7. Тесты

Unit + integration (стенд 212.119.42.100):

1. Два домена: независимые draft/pin/deploy; деплой A не меняет конфиги B.
2. Fan-in: 3 портала → релей → бридж-дефолт + geo-лист: валидация, компиляция,
   деплой, трафик через каждый портал выходит на правильный бридж.
3. Невалидные формы: цикл, 2 default-ветки, geo-лист с исходящей, портал
   с входящей — отвергаются с понятными кодами.
4. Staged-нода с ролью внутри «чужого» набора не мешает доменам.
5. L2TP: install на релее домена, auto-l2tp path, classic sync сохраняет
   L2TP-фрагмент; reinstall — PSK не меняется.
6. Расширение fan-in: добавление 4-го портала в живой домен —
   draft → deploy без даунтайма остальных.
7. Разбиение/слияние компонент (удаление связи посередине) — пересчёт
   доменов, корректные ошибки валидации для «осиротевших» частей.
8. Регрессия: существующий suite (644 теста) зелёный.

Приёмка на стенде: цепочка портал×2 → релей → бридж USA + бридж RU (geo),
проверка трафика (TCP/UDP/скорость/egress IP/geo), Happ на телефоне
(IPv6 fast-reject), L2TP через релей.

## 8. Оценка

- Разработка: 3–5 рабочих дней (валидатор/композер — самая объёмная часть;
  UI-селектор домена; per-domain состояние; тесты).
- Стендовая приёмка: 0,5–1 день.
- Перенос в прод: по отработанному пайплайну v1.3.3.12 (release tag →
  fresh backup → cutover с чекпоинтами), 1–2 часа.

Итого: ~4–6 рабочих дней с приёмкой.

## 9. Открытые вопросы

1. Нужны ли домену человекочитаемые имена (для UI), или достаточно
   автогенерации вида «Домен: порталы X, Y → бридж Z»?
2. Fan-in только «ровно в первый релей» или допустимо слияние веток
   разной длины (портал → релейA → релейB и портал2 → релейB)?
   Предлагаю: разрешить (общее правило «fan-in слева»), это бесплатно
   в рамках дизайна 4.1.
3. L2TP на порталах — точно не нужен в этой итерации?
